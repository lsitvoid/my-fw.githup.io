红黑树

课本把红黑树讲得很玄，其实它只回答一个问题： 怎么让二叉搜索树在最坏情况下也不长歪。

红黑树不追求完全平衡，只保证从根到叶子的最长路径 不超过最短路径的两倍——够用，且旋转次数少。

它的五条家规

  • 每个节点非红即黑
  • 根节点是黑的
  • 叶子（NIL）是黑的
  • 红节点的孩子必须是黑的（不许红红相邻）
  • 任一节点到其每个叶子的路径含相同数目的黑节点

高度的天花板

由第 4、5 条可以推出（引理）：一棵有 n 个内部节点的红黑树， 高度最多 2·log₂(n+1)。直观理解：路径上的红节点不可能相邻， 所以最坏也只是「黑黑黑红黑黑红」——长度至多是纯黑路径的两倍。

插入后怎么修

新节点一律先染红再插入（染黑必然破坏黑高，染红只可能违反「不许红红相邻」）。 冲突修复只看叔叔的颜色：

  • 叔叔是红 → 父叔变黑、祖父变红，冲突上推两层（可能推到根，根永远染黑）
  • 叔叔是黑 → 旋转 + 变色，一次了结

所以插入最多 2 次旋转，其余全靠变色——这是它比 AVL 快的关键。

删除后怎么修（双黑）

删除的麻烦只在删到黑节点时：路径上黑高少 1，出现「双黑」。 修复思路是从兄弟借黑色：

  • 兄弟有红孩子 → 借过来，一次旋转补齐黑高
  • 兄弟全黑且是红 → 兄弟染红，双黑上推给父亲
  • 一路推到根 → 全线黑高减一，结束

删除最多 3 次旋转。

和 AVL 怎么选

  • AVL 严格平衡（高 ≤ 1.44·log n），红黑树宽松（≤ 2·log(n+1)）——纯查询 AVL 更快
  • AVL 插删动辄回溯到根修平衡，红黑树旋转有硬上限（插入 ≤ 2、删除 ≤ 3）——写入密集红黑树更稳
  • 工程取舍：读多写少用 AVL，读写混合、最坏情况敏感（内核、标准库）用红黑树

优点

  • 插入 / 删除 / 查找稳定在 O(log n)
  • 节点只多存 1 bit 颜色，比 AVL 的平衡因子省内存
  • 中序遍历天然有序，适合有序集合、有序映射这类场景

代价

  • 插入删除要处理着色与旋转，实现复杂、代码量大
  • 范围查询要跨子树遍历，效率相对低
  • 节点内存不连续，缓存命中率不如 B 树，高频缓存场景要掂量

在哪见过它

C++ 的 std::map / multimap / multiset、 Java 的 TreeMap / TreeSet、 Linux 内核的 CFS 完全公平调度器、高精度定时器 hrtimer、 epoll 的就绪队列、ext3 文件系统的目录项—— 工业界选它的理由就一条：最坏情况可预期。
